# How LLMs behave: tokens, context, sampling, non-determinism
# Как ведут себя LLM: токены, контекст, сэмплирование, недетерминированность

## Tokens: the unit of input, output, and cost
## Токены: единица входа, выхода и стоимости

Claude does not read characters or words directly. It reads tokens, and the characters-per-token average depends on the tokenizer of the model at hand and differs between model generations. Treat any chars-per-token rule of thumb as model-dependent and confirm current tokenizer behavior at build time. Everything the model processes is counted in tokens: your prompt, the conversation history, tool definitions, tool results, and the response the model generates. Tokens are the unit of both pricing and budget, so when you estimate what a feature costs or whether an input fits, you are counting tokens, not words. A useful habit is to think in tokens, since that is the unit the API bills in and the context window measures.

> Claude не читает символы или слова напрямую. Он читает токены, а среднее число символов на токен зависит от токенизатора конкретной модели и различается между поколениями моделей. Любое эмпирическое правило «столько-то символов на токен» следует считать зависящим от модели и проверять актуальное поведение токенизатора на этапе разработки. Всё, что обрабатывает модель, считается в токенах: ваш промпт, история диалога, определения инструментов (tool definitions), результаты инструментов (tool results) и ответ, который генерирует модель. Токены — это единица и тарификации, и бюджета, поэтому, оценивая стоимость функции или то, поместятся ли входные данные, вы считаете токены, а не слова. Полезная привычка — мыслить токенами, поскольку именно в них API выставляет счёт и измеряется контекстное окно.

## The context window: a fixed budget
## Контекстное окно: фиксированный бюджет

The context window is the total number of tokens the model can take in for a single request. It holds everything at once: the system prompt, the full conversation so far, any documents you inject, every tool result, and the model output. It is a fixed budget with two distinct edge behaviors. A request whose input is already larger than the window is rejected with a validation error before generation begins. A request that fits on input can still reach the ceiling during generation. Current models then stop and return the output generated so far with a model_context_window_exceeded stop reason rather than raising an error. Either way, keeping a long session running requires the application to trim or summarize history before each call. In development, the window rarely fills because test inputs are short. In production, on the other hand, longer inputs and more turns fill the window faster. This is the failure Module 2 explores in detail.

> Контекстное окно (context window) — это общее количество токенов, которое модель может принять в рамках одного запроса. Оно вмещает всё сразу: системный промпт, весь диалог на текущий момент, любые добавленные вами документы, каждый результат инструмента и вывод модели. Это фиксированный бюджет с двумя разными вариантами поведения на границе. Запрос, входные данные которого уже превышают окно, отклоняется с ошибкой валидации ещё до начала генерации. Запрос, который помещается на входе, всё равно может упереться в потолок во время генерации. В этом случае текущие модели останавливаются и возвращают уже сгенерированный вывод с причиной остановки (stop reason) `model_context_window_exceeded`, а не выбрасывают ошибку. В любом случае, чтобы длинная сессия продолжала работать, приложение должно обрезать или суммаризировать историю перед каждым вызовом. При разработке окно заполняется редко, потому что тестовые входные данные короткие. В продакшене же более длинные входные данные и большее число ходов (turns) заполняют окно быстрее. Именно этот сбой подробно разбирается в Модуле 2.

## Sampling: why the same prompt can give different answers
## Сэмплирование: почему один и тот же промпт может давать разные ответы

A language model does not pick one fixed next token. At each step it produces a probability distribution over possible next tokens and then samples from it. Settings, such as temperature, shape that distribution: a lower temperature concentrates probability on the most likely tokens and makes output more repeatable, while a higher temperature spreads it out and makes output more varied. Because the choice is sampled rather than fixed, the same prompt run twice can return different wording even when both answers are correct. This is a property of how the model generates. Note that sampling controls are model-dependent: the newest Claude models do not accept non-default sampling parameters. Setting temperature, top_p, or top_k returns a 400 error, and behavior on those models is steered through prompting instead. Even where temperature is accepted, temperature 0 makes outputs more repeatable but does not guarantee identical outputs across calls. Confirm current parameter support in the API reference at build time.

> Языковая модель не выбирает один заранее определённый следующий токен. На каждом шаге она строит распределение вероятностей по возможным следующим токенам, а затем делает из него выборку (sampling). Настройки, такие как `temperature`, формируют это распределение: более низкая температура концентрирует вероятность на наиболее вероятных токенах и делает вывод более воспроизводимым, а более высокая — размывает распределение и делает вывод более разнообразным. Поскольку выбор делается случайной выборкой, а не фиксирован, один и тот же промпт, запущенный дважды, может вернуть разные формулировки, даже если оба ответа верны. Это свойство самого способа генерации модели. Обратите внимание, что параметры сэмплирования зависят от модели: новейшие модели Claude не принимают параметры сэмплирования со значениями, отличными от значений по умолчанию. Установка `temperature`, `top_p` или `top_k` возвращает ошибку 400, и поведением таких моделей управляют через промптинг. Даже там, где `temperature` поддерживается, `temperature` 0 делает вывод более воспроизводимым, но не гарантирует идентичных результатов между вызовами. Проверяйте актуальную поддержку параметров в справочнике API (API reference) на этапе разработки.

## Non-determinism: what it means for testing and evals
## Недетерминированность: что это значит для тестирования и eval-ов

Non-determinism is the primary consequence of sampling: identical inputs do not guarantee identical outputs. That changes how you test a Claude feature. A test that asserts the exact text of a response will be inconsistent, because the model can express the same correct answer many ways. Instead, assert on the property that must hold: a required field is present, a value is in range, the structure parses. When you need to judge meaning rather than structure, use an eval with a model-graded judge. This is why the course treats evals as the standard for knowing a feature is correct, and why Module 3 builds that capability.

> Недетерминированность — главное следствие сэмплирования: идентичные входные данные не гарантируют идентичного вывода. Это меняет подход к тестированию функций на базе Claude. Тест, который проверяет (assert) точный текст ответа, будет нестабильным, потому что модель может выразить один и тот же правильный ответ множеством способов. Вместо этого проверяйте свойство, которое обязано выполняться: обязательное поле присутствует, значение находится в допустимом диапазоне, структура успешно парсится. Когда нужно оценить смысл, а не структуру, используйте eval с судьёй, оценивающим с помощью модели (model-graded judge). Именно поэтому курс рассматривает eval-ы как стандарт для подтверждения корректности функции, и именно поэтому в Модуле 3 эта возможность выстраивается.
