# Choosing the right scope for state that survives sessions
# Выбор правильной области действия для состояния, которое сохраняется между сессиями

The agent from the previous section runs correctly within a single session. What it cannot do is remember anything when that session ends. Memory scope is how you decide what the agent should know at the start of the next session, and how much it costs to carry that knowledge forward.

> Агент из предыдущего раздела корректно работает в рамках одной сессии. Чего он не умеет — так это помнить что-либо после окончания сессии. Область действия памяти (memory scope) — это способ решить, что агент должен знать в начале следующей сессии и во что обойдётся перенос этих знаний.

## Memory patterns and when each is right
## Паттерны памяти и когда каждый из них уместен

Beyond memory scope, the blueprint groups several agent design patterns under this objective, and you have already built each one earlier in this module. The tool-use loop, where the model calls a tool, reads the result, and continues, is the core pattern from the tool-use and agent-construction clusters. Multi-step task decomposition breaks a goal into ordered subtasks, and planning-and-execution separates deciding the plan from carrying it out, the same split the human-in-the-loop check after a planning step guards. Memory scope, covered next, is the pattern that decides what state survives once the loop ends.

> Помимо области действия памяти, в программе (blueprint) под этой целью сгруппировано несколько паттернов проектирования агентов, и каждый из них вы уже построили ранее в этом модуле. Цикл tool use, в котором модель вызывает инструмент, читает результат и продолжает работу, — основной паттерн из блоков об использовании инструментов и построении агентов. Многошаговая декомпозиция задачи разбивает цель на упорядоченные подзадачи, а разделение планирования и выполнения (planning-and-execution) отделяет выбор плана от его исполнения — то самое разделение, которое охраняет проверка с участием человека после этапа планирования. Область действия памяти, о которой пойдёт речь дальше, — это паттерн, определяющий, какое состояние сохранится после завершения цикла.

Memory scope sets what an agent knows when a new session starts. Making the wrong choice has two failure modes, and they pull in opposite directions:

- **Too much state in-context** inflates every API call, because the model re-reads the full conversation on every turn and the bill scales with session length.
- **Too little state in persistent storage** strips the agent of memory across sessions, because anything not written down disappears the moment the conversation ends.

> Область действия памяти определяет, что агент знает в начале новой сессии. У неверного выбора два вида сбоев, и они тянут в противоположные стороны:
>
> - **Слишком много состояния в контексте** раздувает каждый вызов API, потому что модель на каждом ходе заново читает весь диалог, и счёт растёт вместе с длиной сессии.
> - **Слишком мало состояния в постоянном хранилище** лишает агента памяти между сессиями, потому что всё, что не записано, исчезает в момент окончания диалога.

| Scope | What persists | Cost | When to use | What you lose |
|---|---|---|---|---|
| **In-context memory** | State lives in the active conversation and survives turns within a single session. | Zero retrieval overhead; inflates token cost as conversation grows | Short sessions where all the state the agent needs fits inside the context window and nothing has to carry across restarts. | Everything once the session ends. A clear command or a new session wipes the state. |
| **External storage** | State is written to a database and read back at session start or on demand. | Each database call adds retrieval latency, and you take on the engineering work of read and write logic. | State that has to survive across sessions, move between users, or be shared across multiple agent instances. | Nothing on the persistence side. The cost shows up as latency on every call and ongoing implementation complexity. |
| **Summarized memory** | A condensed version of prior conversation is generated and injected at the start of the next session. | Lower token cost per session than replaying full history, but the summarization step drops detail that was in the original. | Long-running conversational agents where the full history would outgrow the context budget before the conversation is done. | Any detail the summarizer did not preserve. The agent only sees what the summarization prompt chose to keep. |
| **No persistent memory (stateless)** | Nothing. Each session is independent. | No overhead at all, since there is nothing to retrieve or store. | Task-execution agents that finish and close out, or pipelines where every session is fully independent by design. | All prior context. If a follow-up depends on something from an earlier session, the agent has no way to reach it. |

| Область действия | Что сохраняется | Стоимость | Когда использовать | Что вы теряете |
|---|---|---|---|---|
| **Память в контексте (in-context)** | Состояние находится в активном диалоге и сохраняется между ходами в рамках одной сессии. | Нулевые накладные расходы на извлечение; стоимость в токенах растёт по мере роста диалога | Короткие сессии, где всё нужное агенту состояние помещается в контекстное окно и ничего не нужно переносить между перезапусками. | Всё после окончания сессии. Команда очистки (clear) или новая сессия стирает состояние. |
| **Внешнее хранилище** | Состояние записывается в базу данных и считывается обратно при старте сессии или по запросу. | Каждое обращение к базе данных добавляет задержку на извлечение, и на вас ложится инженерная работа по логике чтения и записи. | Состояние, которое должно сохраняться между сессиями, переходить между пользователями или быть общим для нескольких экземпляров агента. | Ничего с точки зрения сохранности. Цена проявляется в задержке каждого вызова и постоянной сложности реализации. |
| **Суммаризированная память** | Сжатая версия предыдущего диалога генерируется и добавляется в начало следующей сессии. | Ниже стоимость в токенах на сессию, чем при воспроизведении всей истории, но на этапе суммаризации теряются детали, которые были в оригинале. | Долго работающие диалоговые агенты, у которых полная история переросла бы бюджет контекста до завершения диалога. | Любые детали, которые суммаризатор не сохранил. Агент видит только то, что решил оставить промпт суммаризации. |
| **Без постоянной памяти (stateless)** | Ничего. Каждая сессия независима. | Никаких накладных расходов, поскольку нечего извлекать или хранить. | Агенты для выполнения задач, которые завершают работу и закрываются, или пайплайны, где каждая сессия полностью независима по замыслу. | Весь предыдущий контекст. Если продолжение зависит от чего-то из более ранней сессии, у агента нет способа до этого добраться. |

## Choosing a memory scope at agent design time
## Выбор области действия памяти на этапе проектирования агента

The choice of how an agent remembers prior interactions belongs in the design phase, not the production refactor. An agent that helps the same user across multiple days needs to carry state between sessions, which means storing summaries or full history outside the model's context window so the next session can read them back. An agent that receives a single job, completes it, and closes it out has no prior session to recall, so it runs stateless.

> Решение о том, как агент запоминает предыдущие взаимодействия, принимается на этапе проектирования, а не при рефакторинге в продакшене. Агенту, который помогает одному и тому же пользователю на протяжении нескольких дней, нужно переносить состояние между сессиями, а значит, хранить краткие изложения или полную историю за пределами контекстного окна модели, чтобы следующая сессия могла их прочитать. Агенту, который получает одно задание, выполняет его и завершает работу, вспоминать нечего — у него нет предыдущей сессии, поэтому он работает без состояния (stateless).

The default path looks reasonable at first. You store the full conversation history in the messages array, send it on every API call, and the prototype works. It keeps working for a while. The trouble starts further in, when token cost scales with every additional turn, latency climbs as the context window fills, and eventually a long session hits the hard limit and the agent stops responding. At that point, you need to refactor: pull conversation state out of the live context, put it in external storage, and add only what each turn needs. The refactor itself is mechanical, a few hundred lines of code and a database the team already has. What it costs is timing. The work happens under production pressure, usually with a deadline already in motion, and every hour spent restructuring memory is an hour not spent on whatever the agent is supposed to do next. Making the call during design phase is cheap, while doing it when it's time to refactor is more expensive.

> Путь по умолчанию поначалу выглядит разумно. Вы храните всю историю диалога в массиве messages, отправляете её при каждом вызове API, и прототип работает. Какое-то время он продолжает работать. Проблемы начинаются позже: стоимость в токенах растёт с каждым новым ходом, задержка увеличивается по мере заполнения контекстного окна, и в итоге длинная сессия упирается в жёсткий лимит, и агент перестаёт отвечать. В этот момент нужен рефакторинг: вынести состояние диалога из активного контекста, поместить его во внешнее хранилище и добавлять только то, что нужно на каждом ходе. Сам рефакторинг механический — несколько сотен строк кода и база данных, которая у команды уже есть. Дорого обходится время. Работа идёт под давлением продакшена, обычно когда дедлайн уже близко, и каждый час, потраченный на перестройку памяти, — это час, не потраченный на то, что агент должен делать дальше. Принять решение на этапе проектирования дёшево, а когда дело доходит до рефакторинга — значительно дороже.

The content below outlines three memory approaches and the conditions where each fits, the overhead each carries, and the assumption that most often pushes teams toward the wrong choice.

> Ниже описаны три подхода к памяти: условия, в которых подходит каждый из них, связанные с ними накладные расходы и предположение, которое чаще всего подталкивает команды к неверному выбору.

| | |
|---|---|
| **Handles well** | The memory scope matches the task at design time. Use external storage when the agent continues a thread across sessions. Use stateless when each job is self-contained. Use in-context when the session is short and does not need to survive a restart. |
| **Adds cost or complexity** | External storage adds retrieval latency and the read/write logic that goes with it. Summarized memory depends on a well-specified summarizer prompt; without one, task-critical state gets dropped on every compression. Neither approach is free, so weigh the costs and choose wisely. |
| **Use a different approach** | Holding all state in-context on the assumption that the window will be large enough. Token cost grows with every additional turn because the full context is sent on each API call. Without caching or compaction, long sessions accumulate cost faster than teams expect when they only measure early turns. Measure actual session token usage against the window limit before committing. |

| | |
|---|---|
| **Хорошо подходит** | Область действия памяти соответствует задаче уже на этапе проектирования. Используйте внешнее хранилище, когда агент продолжает работу над темой в нескольких сессиях. Используйте режим без состояния, когда каждое задание самодостаточно. Используйте память в контексте, когда сессия короткая и не должна переживать перезапуск. |
| **Добавляет затрат или сложности** | Внешнее хранилище добавляет задержку на извлечение и сопутствующую логику чтения и записи. Суммаризированная память зависит от хорошо проработанного промпта суммаризатора; без него критически важное для задачи состояние теряется при каждом сжатии. Ни один из подходов не бесплатен, поэтому взвешивайте затраты и выбирайте с умом. |
| **Используйте другой подход** | Хранение всего состояния в контексте в расчёте на то, что окна хватит. Стоимость в токенах растёт с каждым новым ходом, потому что весь контекст отправляется при каждом вызове API. Без кэширования или сжатия длинные сессии накапливают стоимость быстрее, чем ожидают команды, измеряющие только первые ходы. Прежде чем принять решение, измерьте фактическое использование токенов за сессию относительно лимита окна. |

## Skills: reusable instruction sets that load on demand without inflating every session
## Skills: многократно используемые наборы инструкций, которые загружаются по требованию и не раздувают каждую сессию

The memory scope table above covers how an agent carries state across sessions. There is a related but distinct problem: how you carry repeatable instructions across tasks without paying to inject them into every session. The pattern for that is a Skill, a reusable markdown file that teaches Claude how to handle a specific kind of task once. Claude loads the Skill automatically when a request matches its description. The instructions sit on disk until they are needed; they are not resident in every conversation.

> Таблица областей действия памяти выше описывает, как агент переносит состояние между сессиями. Есть связанная, но отдельная проблема: как переносить повторяющиеся инструкции между задачами, не платя за их добавление в каждую сессию. Паттерн для этого — Skill: многократно используемый markdown-файл, который один раз учит Claude справляться с определённым видом задач. Claude автоматически загружает Skill, когда запрос соответствует его описанию. Инструкции лежат на диске, пока не понадобятся, и не присутствуют постоянно в каждом диалоге.

A Skill lives in a `SKILL.md` file inside an identified directory. The file has two parts: a frontmatter block with a name and a description, and the instructions below it. The description is the matching criterion. When you send a request, Claude reads the name and description of every available Skill, compares them against your message, and loads the full instructions only when there is a match. If the instructions are not relevant to the current request, they never enter the context window.

> Skill хранится в файле `SKILL.md` внутри отдельной директории. Файл состоит из двух частей: блока frontmatter с именем (name) и описанием (description) и инструкций под ним. Описание служит критерием соответствия. Когда вы отправляете запрос, Claude читает имя и описание каждого доступного Skill, сопоставляет их с вашим сообщением и загружает полные инструкции только при совпадении. Если инструкции не относятся к текущему запросу, они вообще не попадают в контекстное окно.

This is the key contrast with the memory patterns in the table above. In-context memory is always present and grows with every turn. `CLAUDE.md` behavior depends on where you are running Claude Code. In the Claude Code CLI, a `CLAUDE.md` file loads into every session regardless of what task is running. In the Agent SDK, whether filesystem settings including `CLAUDE.md` load is controlled by the `settingSources` configuration. Do not rely on a default: set it explicitly to the sources you intend, and confirm current default behavior against the Agent SDK reference at build time. A Skill, by contrast, loads only when the task calls for it, in both environments. For instruction sets that apply to specific recurring tasks rather than to every session, Skills are a lower-overhead pattern than either alternative.

> В этом ключевое отличие от паттернов памяти из таблицы выше. Память в контексте присутствует всегда и растёт с каждым ходом. Поведение `CLAUDE.md` зависит от того, где вы запускаете Claude Code. В Claude Code CLI файл `CLAUDE.md` загружается в каждую сессию независимо от выполняемой задачи. В Agent SDK загрузка настроек из файловой системы, включая `CLAUDE.md`, управляется конфигурацией `settingSources`. Не полагайтесь на значение по умолчанию: явно задайте нужные источники и проверьте актуальное поведение по умолчанию в справочнике Agent SDK на этапе разработки. Skill же, напротив, загружается только тогда, когда этого требует задача, — в обеих средах. Для наборов инструкций, которые относятся к конкретным повторяющимся задачам, а не к каждой сессии, Skills — паттерн с меньшими накладными расходами, чем любая из альтернатив.

### Skills vs. CLAUDE.md vs. in-context instructions: choosing the right pattern
### Skills, CLAUDE.md или инструкции в контексте: выбор правильного паттерна

| Pattern | When it loads | Context cost | Best for |
|---|---|---|---|
| **Skill** (`SKILL.md`) | On demand when request matches skill's description | Low. Only the name and description load at startup; full content loads only on match | Task-specific expertise that should not inflate sessions where it is not needed. *Examples include domain-specific output formats, specialized review checklists, and workflows that apply to a subset of tasks rather than every interaction.* |
| **`CLAUDE.md`** | Every session, unconditionally | Fixed overhead per session regardless of task | Always-on project standards that apply to everything. *Examples include coding conventions the team has standardized on, output format rules the project requires, and constraints that hold across all tasks in the codebase.* |
| **In-context instructions** | Present for every turn within that session | Grows with session length; does not survive session end | Short sessions where the full history fits within the window and nothing needs to persist. *Examples include one-off exploratory work and tasks scoped to a single conversation.* |

| Паттерн | Когда загружается | Стоимость контекста | Лучше всего подходит для |
|---|---|---|---|
| **Skill** (`SKILL.md`) | По требованию, когда запрос соответствует описанию skill | Низкая. При запуске загружаются только имя и описание; полное содержимое загружается только при совпадении | Экспертиза под конкретные задачи, которая не должна раздувать сессии, где она не нужна. *Примеры: форматы вывода для конкретной предметной области, специализированные чек-листы для ревью и процессы, которые относятся к подмножеству задач, а не к каждому взаимодействию.* |
| **`CLAUDE.md`** | В каждой сессии, безусловно | Фиксированные накладные расходы на каждую сессию независимо от задачи | Постоянно действующие стандарты проекта, которые применяются ко всему. *Примеры: соглашения о стиле кода, принятые командой, правила формата вывода, которых требует проект, и ограничения, действующие для всех задач в кодовой базе.* |
| **Инструкции в контексте** | Присутствуют на каждом ходе в рамках данной сессии | Растёт с длиной сессии; не сохраняется после её окончания | Короткие сессии, где вся история помещается в окно и ничего не нужно сохранять. *Примеры: разовая исследовательская работа и задачи, ограниченные одним диалогом.* |

## Current availability: Skills on the Messages API
## Текущая доступность: Skills в Messages API

Skills are available on the Messages API today, but the integration is in beta and the configuration is not the same as the Claude Code or Agent SDK paths. Two beta headers are required on the API request: `code-execution-2025-08-25` and `skills-2025-10-02`. Skills invoked this way run inside the code execution container rather than in the calling application's environment, which has implications for what tools and filesystem access the Skill can rely on.

> Skills уже сейчас доступны в Messages API, но эта интеграция находится в бете, а её конфигурация отличается от вариантов с Claude Code или Agent SDK. В запросе к API требуются два beta-заголовка: `code-execution-2025-08-25` и `skills-2025-10-02`. Вызванные таким образом Skills выполняются внутри контейнера для выполнения кода (code execution container), а не в среде вызывающего приложения, и это влияет на то, на какие инструменты и доступ к файловой системе может рассчитывать Skill.

Beta headers are versioned and change as features move toward general availability. Before building against this configuration in production, check the current Anthropic API documentation to confirm the header values, whether the feature has reached general availability, and whether the code execution container is still the runtime path.

> Beta-заголовки версионируются и меняются по мере того, как функции движутся к общей доступности (general availability). Прежде чем строить продакшен-решение на этой конфигурации, проверьте актуальную документацию Anthropic API: значения заголовков, достигла ли функция общей доступности и по-прежнему ли контейнер для выполнения кода является средой выполнения.

One important constraint: subagents do not automatically inherit Skills from the parent session. When you delegate a task to a subagent, it starts with a clean context. Note that while Skills and conversation history do not carry over, subagents do inherit the permission context from the parent session; permission scope is not reset at delegation. If the subagent needs a Skill, you must explicitly list it in the subagent's configuration. This matters at agent design time: if you are wiring a subagent to perform a task that depends on specific instructions, those instructions need to be registered against the subagent, not assumed to carry over from the parent.

> Одно важное ограничение: субагенты не наследуют Skills от родительской сессии автоматически. Когда вы делегируете задачу субагенту, он начинает с чистого контекста. Обратите внимание: хотя Skills и история диалога не переносятся, контекст разрешений (permission context) субагенты от родительской сессии наследуют — область разрешений при делегировании не сбрасывается. Если субагенту нужен Skill, его необходимо явно указать в конфигурации субагента. Это важно на этапе проектирования агента: если вы подключаете субагента для выполнения задачи, зависящей от конкретных инструкций, эти инструкции нужно зарегистрировать для субагента, а не рассчитывать, что они перейдут от родителя.
